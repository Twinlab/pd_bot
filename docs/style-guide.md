# Разработка

Бот рассчитан на один небольшой сервер. Изменения должны упрощать сопровождение
и сохранять существующие сценарии: дополнительные сервисы и поддержка нескольких
серверов не нужны для текущего назначения проекта.

## Среда

Нужен Python 3.13+ и отдельное виртуальное окружение. После его активации установите
зависимости разработки:

```bash
python -m pip install -e ".[dev]"
```

Подготовка окружения описана в [начале работы](getting-started.md). Для обычной
разработки достаточно линтеров и тестов: подключение бота к Discord и локальный
запуск Lavalink не требуются. Используйте тестовые настройки и отдельный checkout
без боевого `.env` и рабочих данных.

Источником зависимостей остаётся `pyproject.toml`. Dockerfile и CI устанавливают их
через `pip`; `uv.lock` сейчас не участвует в сборке. Настройки Ruff, mypy и pytest
также находятся в `pyproject.toml`.

## Куда вносить изменение

| Задача | Место и ориентир |
| --- | --- |
| Команда или событие Discord | `cogs/`; расширение экспортирует `async def setup(bot)` |
| Работа с БД | Соответствующий `*_data_manager.py`, модели — в `utils/models.py` |
| Сетевой запрос | API-клиент в `utils/`; HTTP не должен быть спрятан внутри рендера |
| Кнопки, формы и карточки | Представления подсистемы; общие элементы — `utils/ui/` |
| Настройка поведения | Модель в `config/settings.py` и значение в YAML |
| Исправление ошибки | Ближайший тест в `tests/test_cogs/`, `tests/test_utils/` или `tests/test_handlers/` |

Не переносите логику БД и внешних API в обработчики кнопок. Например, привязки
профиля разделены на `utils/profile/accounts.py`, `account_views.py` и
`utils/profile_accounts_data_manager.py`: проверка аккаунта, интерфейс и запись
в БД решают разные задачи.

При изменении схемы отдельно подготовьте миграцию существующих данных и проверку
восстановления из резервной копии. `generate_schemas()` при запуске создаёт
отсутствующие таблицы, но не обновляет произвольным образом уже существующие.

## Команды и интерфейс

Для новой команды выбирайте существующий в подсистеме способ регистрации:
`hybrid_command` при поддержке префикса и slash-вызова, `app_commands` для
интерактивных slash-сценариев. Обрабатывайте ошибки через
`utils/error_handler.py`: `command_error_handler`, `safe_send` и `safe_send_error`.

Проверки доступа должны действовать в самом обработчике. Скрытие кнопки или
`default_permissions` не заменяет проверку пользователя и его прав. У операций
подтверждения повторно проверяйте актуальность состояния: между превью и кликом
могут измениться привязки, роль, блокировка или время ожидания.

Перед долгим запросом подтверждайте interaction через `defer()`, затем используйте
предусмотренный ответ или followup. Не подтверждайте один interaction дважды.
Личные формы, ошибки и подтверждения отправляйте эфемерно; общие карточки —
публично. При перепубликации текста пользователя задавайте `allowed_mentions`
явно, чтобы случайно не создавать уведомления.

Карточки и интерактивные панели используют Components V2 (`LayoutView`).
Общие изображения с текстом и ссылками собирайте через `utils.ui.image_card`,
цвета берите из `utils.ui.colors`. Не смешивайте CV2 с `content` или `embed`
в одном сообщении. Для простых существующих ответов с обычным `Embed` отдельная
миграция интерфейса не требуется.

Постоянным кнопкам нужны стабильные идентификаторы с префиксом функции и
регистрация при загрузке кога. Пример — `cogs/role_reaction.py` и
`utils/role_reaction_views.py`. Для временной панели задавайте срок жизни и
корректно обрабатывайте закрытый или устаревший экземпляр.

## Асинхронный код и состояние

- Переиспользуйте HTTP-сессию и закрывайте её в lifecycle владельца. Задавайте
  таймаут, ограничение объёма ответа и разумные повторы временных ошибок.
- Рендер и блокирующие файловые операции выносите из цикла событий через
  `asyncio.to_thread`. Независимые запросы можно выполнять параллельно, но с лимитом.
- Храните ссылки на созданные фоновые задачи. При выгрузке отменяйте их и
  дожидайтесь завершения там, где требуется освободить ресурсы.
- Защищайте общую изменяемую структуру одной блокировкой на операцию. Запись
  нескольких связанных строк должна использовать транзакцию.
- При повторе сохранения статистики повторяйте фиксированный незаписанный
  интервал, а не расчёт от старого старта до нового текущего времени.
- После `await` состояние могло измениться. Это особенно важно для дедлайнов,
  отмены публикации и редактирования уже финализированной карточки.

Подробности хранения и жизненного цикла — в [архитектуре](architecture.md).

## Стиль

Идентификаторы пишутся по-английски, пользовательские строки, комментарии и
описания функций — по-русски. Для публичных функций нужны аннотации типов;
используйте `list[int]`, `dict[str, str]`, `str | None`. Docstring описывает
назначение и нетривиальные аргументы, результат или ошибки в формате Google.

Ruff задаёт длину строки 100, двойные кавычки и порядок импортов. Комментарий
должен объяснять причину или ограничение, а не пересказывать следующую строку.
Для журналирования используйте `logging.getLogger("bot.<подсистема>")`.
Не записывайте токены, пароли, заголовки авторизации и полные секретные конфигурации.

## Проверки

Сначала проверяйте затронутую подсистему. Например, для голосовой статистики:

```bash
python -m pytest tests/test_cogs/test_user_stats_cog.py
python -m ruff check cogs/user_stats.py
python -m ruff format --check cogs/user_stats.py
python -m mypy cogs/user_stats.py
```

Для применения форматирования используйте `python -m ruff format` с явным списком
изменённых исходников. В текущей конфигурации Ruff и mypy исключают `tests/`;
успешная проверка `.` не означает отдельную проверку стиля и типов тестов.

Перед коммитом выполните полный набор:

```bash
python -m ruff check .
python -m ruff format --check .
python -m pytest
python -m mypy .
```

CI проверяет Ruff, форматирование и pytest. Mypy запускается отдельно и сейчас
не входит в workflow. Проверки не требуют запуска `main.py`.

Для регрессии важен наблюдаемый результат: счётчик, права, состояние БД, отправленная
карточка или отсутствие повторной публикации. При изменении асинхронной логики
проверяйте таймауты, повтор после сбоя, отмену и два одновременных действия.
Для статистики отдельно проверяйте границу московского дня.

В тестах используйте `AsyncMock` для ожидаемых корутин, `MagicMock` для обычных
объектов, управляемое время и события `asyncio.Event` для воспроизведения гонок.
Сетевые API и Discord подменяйте; БД должна быть временной. Для CV2 доступны
помощники `utils.ui.testing`, позволяющие проверить текст, изображения, ссылки
и цвета независимо от вложенности компонентов.

Если меняется пользовательское поведение, обновите [справочник команд](commands.md)
и подходящий раздел документации вместе с кодом. Документацию можно проверить
локально без запуска бота:

```bash
python -m pip install -e ".[docs]"
python -m mkdocs build --strict
```

В `docs/` находятся только публичные страницы. Личные инструкции по серверу,
сырые логи, разовые диагностики и черновики храните вне репозитория: отсутствие
страницы в меню само по себе не исключает её из сборки MkDocs. Для новой страницы
добавьте пункт в `mkdocs.yml`. Строгая сборка проверяет навигацию, внутренние ссылки
и якоря; после изменения меню просмотрите результат локально через
`python -m mkdocs serve`.
