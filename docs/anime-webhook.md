# Аниме-постинг без постоянно работающего бота

`Anime webhook poster` проверяет расписание каждые 15 минут (в :07, :22, :37, :52).
Время публикаций остаётся 10:00 и 18:00 UTC (13:00 и 21:00 МСК); фактическая отправка
происходит на первой успешной проверке после этого времени. ПК и основной бот могут
быть выключены. Постинг не использует bot token, Discord Gateway, SQLite, Lavalink или сторонние Python-пакеты.

## Настройка и первый запуск

1. Создайте вебхук в нужном текстовом канале Discord. Задайте имя и аватар отправителя.
2. В Settings → Secrets and variables → Actions добавьте `ANIME_WEBHOOK_URL`.
   URL содержит секрет: не публикуйте его в коде, issues или логах.
3. При необходимости добавьте `DANBOORU_LOGIN` и `DANBOORU_API_KEY`; без них поиск
   работает анонимно. Не используйте здесь полный `.env` бота.
4. После появления workflow в `main` откройте Actions → Anime webhook poster →
   Run workflow → `initialize-history`. Это сохраняет начальную историю без отправки.
5. Запустите `preview`: выбирает подходящий пост и выводит ссылку без отправки.
6. Остановите локальный бот (Ctrl+C), если он больше не нужен. Если он должен продолжать
   работать, сначала отключите его аниме-расписание; два планировщика имеют отдельную историю.
7. Запустите `publish` и проверьте сообщение в канале. Следующие публикации идут по расписанию.

В форме Run workflow доступны необязательные параметры:

- `rating`: `auto` — случайный рейтинг из конфига; `g`, `s`, `q`, `e` — заданный рейтинг.
- `tag`: один тег Danbooru, например `genshin_impact` или `suzumiya_haruhi`; пусто — автоподбор.

Параметры применяются к `preview` и `publish` одного ручного запуска. Плановое расписание
всегда использует конфиг. При явном теге, как у `/post_anime`, базовые теги и исключения
автоподбора не применяются; минимальная оценка, выбранный рейтинг и защита от повторов
сохраняются. Несколько тегов, `rating:` и другие метатеги в поле `tag` не принимаются.
Если подходящих постов нет, публикация завершается ошибкой без подмены тега или рейтинга.

Ручной `publish` добавляет одну публикацию и не отменяет ближайшую плановую.
Режим `scheduled` вручную проверяет расписание: отправляет один уже наступивший, но
ещё не опубликованный слот текущего дня либо ничего не делает. Рейтинг и тег в этом
режиме берутся из конфига.
Повтор того же GitHub run не публикует уже подтверждённый слот повторно.
Ветка запуска — только `main`. Коммиты, push и изменение серверного развёртывания
этому workflow не требуются: у GITHUB_TOKEN только `contents: read` и `actions: read`.

## Фильтры и оформление

Настройки независимого постера — `config/anime_poster.json`. Начальные значения перенесены
из секции `anime` основного YAML: рейтинги g/s, оценка от 50, базовые теги, франшизы,
исключения и размер выборки. Дальнейшие изменения YAML не обновляют JSON автоматически.
Оформление — Components V2: ссылка на пост, картинка, художник, оценка и рейтинг.

`ops/anime-poster-seed.json` содержит только ID ранее опубликованных картинок,
экспортированные из восстановленной рабочей БД; пользовательских данных и токенов нет.

Локальная проверка без Discord и без изменения истории:

```powershell
.venv\Scripts\python.exe -B ops/anime_poster.py local-preview --rating g --tag genshin_impact
```

## История и сбои

Снимки выбираются по времени создания на всех страницах API, а не по числовому ID.
Ручной режим `reconcile-history` сводит подтверждённые ID и слоты из ещё доступных
результатов запусков в новый журнал. Он полезен после чтения устаревшего снимка:
не публикует картинки и сохраняет незавершённую отправку новейшего снимка для
ручного разбора. Публикация из поля `pending` не считается подтверждённой.

История последних 2000 ID и слотов хранится в артефактах `anime-poster-state-*`, срок
хранения каждого снимка — 90 дней. Каждая публикация обновляет снимок; пустые проверки
артефакты не создают. Перед HTTP-отправкой отдельно сохраняется `pending`, после подтверждения Discord — результат.
Запуски сериализованы через concurrency. Не удаляйте историю или все workflow runs:
без снимка плановая отправка блокируется, а не начинает коллекцию заново.
Сохраняйте свежий артефакт отдельно перед длительным отключением расписания.

Если Discord принял сообщение, но ответ потерялся, автоматический повтор запрещён.
Следующий запуск завершится ошибкой о незавершённой отправке. Посмотрите последний
`state.json` и канал Discord, сопоставьте ID Danbooru:

- `confirm-sent` — подтвердить, что сообщение уже есть; отметить пост и слот отправленными.
- `confirm-not-sent` — подтвердить, что публикации точно не было; снять резервирование.

Оба режима только обновляют журнал. Для повторной проверки планового слота запустите
`scheduled`, для дополнительной ручной публикации — `publish`. Если результат
не удалось достоверно определить, оставьте pending для ручного разбора.

Расписание Actions может задерживаться или пропускаться при высокой нагрузке; точного
SLA нет. Повторные проверки догоняют пропущенные слоты только текущего UTC-дня,
по одному за запуск. Если утро и вечер пропущены, сначала публикуется утро, затем
следующая проверка публикует вечер. За прошлые дни массовая рассылка не выполняется.
Слот в журнале не зависит от cron, поэтому повторная проверка не создаёт дубли.
История от старого расписания также учитывается. В публичном репозитории
расписания отключаются после 60 дней отсутствия активности в репозитории; их надо
включить заново. Стандартные исполнители бесплатны для публичных репозиториев;
в приватном репозитории проверьте общий остаток включённых минут и хранилища Actions.

Настройка политики не доказывает доставку: после первого ручного запуска проверьте
картинку в Discord и первый утренний/вечерний запуск в Actions.
