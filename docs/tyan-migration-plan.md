# Ручной выпуск /tyan

Добавляется одна таблица `tyan_rolls` в существующую SQLite БД на VM.
Старые таблицы, данные и зависимости не меняются.
SQL: [20260910_tyan.sql](../ops/migrations/20260910_tyan.sql).

Одна запись на участника и московскую дату хранит параметры, стабильные ID слов,
готовую строку и время выдачи. События `mother` и `none` хранятся здесь же,
поэтому их общий перерыв сохраняется после перезапуска.

## Локальная подготовка

Генератор, ORM-модель, менеджер истории, настройки и команда добавлены в код.
Тесты применяют ручной SQL к временной SQLite, затем работают через настоящую ORM:
проверяют повторный вызов, переподключение, московскую полночь, конкурентные запросы,
общий перерыв событий и восстановление после ошибок записи/отправки.

Боевая БД не используется локальными тестами. Перед первым выпуском таблицу
нужно отдельно создать на VM после проверки backup, по шагам ниже.

## Последовательность выпуска

1. Выполнить проверки перед коммитом по `AGENTS.md`.
2. До публикации нового образа создать на VM отдельный согласованный SQLite backup
   и проверить его целостность. Не копировать только основной файл открытой WAL-БД.
3. Применить SQL одной транзакцией. Проверить столбцы, уникальный индекс
   `(discord_user_id, date)` и `PRAGMA integrity_check`.
4. После разрешения на commit/push выпустить код через штатный CI → GHCR → Watchtower.
   Compose, окружение и существующие сервисы менять не требуется.
5. Сверить точную ревизию контейнера и стартовый лог; проверить наличие `/tyan`
   в зарегистрированных командах. В Discord вызвать команду дважды от одного
   пользователя: карточка должна остаться прежней, в таблице должна быть одна запись.

## Команды на VM

Сначала доставить проверенный файл SQL на VM, например в
`/home/twinlab/pd_bot_backups/tyan-release/20260910_tyan.sql`, и сравнить SHA-256
с локальным файлом. Команды ниже выполняются на VM, не на Windows.
Путь `release_dir` должен быть новым для каждой попытки; `mkdir` остановит
повторное использование существующего каталога.

```bash
set -euo pipefail
umask 077
db=/home/twinlab/pd_bot/data/bot_data.db
sql=/home/twinlab/pd_bot_backups/tyan-release/20260910_tyan.sql
release_dir="/home/twinlab/pd_bot_backups/tyan-$(date -u +%Y%m%dT%H%M%SZ)"
test -f "$db"
test -f "$sql"
mkdir "$release_dir"

sqlite3 "$db" "PRAGMA busy_timeout=30000; VACUUM INTO '$release_dir/before.db';"
test "$(sqlite3 "$release_dir/before.db" 'PRAGMA integrity_check;')" = "ok"
test -z "$(sqlite3 "$release_dir/before.db" 'PRAGMA foreign_key_check;')"

sqlite3 -bail "$db" <<SQL
.timeout 30000
BEGIN IMMEDIATE;
.read $sql
COMMIT;
SQL

test "$(sqlite3 "$db" 'PRAGMA integrity_check;')" = "ok"
sqlite3 "$db" 'PRAGMA table_info(tyan_rolls); PRAGMA index_list(tyan_rolls);'
```

Backup остаётся на VM в каталоге выпуска с закрытыми правами. Эти команды
не отправляют его в Discord и не меняют политику штатных ежедневных копий.

Штатная инициализация Tortoise умеет создавать отсутствующие таблицы,
но при этом не делает backup. Поэтому ручная миграция должна предшествовать
публикации образа, а не рассчитывать на создание таблицы при старте.

## Откат

Вернуть предыдущий образ по сохранённому digest; новую таблицу оставить.
Старому боту она не мешает. Удаление таблицы и восстановление всей БД
для отката приложения не нужны: это потеряло бы новые данные других модулей.
